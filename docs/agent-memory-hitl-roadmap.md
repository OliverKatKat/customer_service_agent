## 推荐架构

`tenant_id` 表示商家或组织，`customer_id` 表示该租户内的客户，`ticket_id` 表示单次工单，`conversation_id` 表示 Agent 会话，`request_id` 表示一次异步执行；OpenTelemetry `trace_id` 只表示链路追踪 ID。所有这些字段应分别命名，不能再用工单 ID 冒充 trace ID。

身份从服务端 JWT 与数据库解析并验证，缺少 `tenant_id` 或 `customer_id` 时拒绝访问；不接受 prompt、请求体或 Agent 工具参数提供的租户身份。API -> Celery -> LangGraph -> DB/Qdrant/工具使用同一份不可由模型修改的受信任上下文。

记忆分层：会话消息仍按租户与会话保存；长期客户记忆按 `tenant_id + customer_id` 检索，保留 `ticket_id` 作为来源；租户知识库只按租户检索。Qdrant 共享集合方案需在所有读取路径强制同时过滤租户与客户，写入时包含两者；如需更强隔离，可再评估独立集合/实例和数据库行级安全策略。相同租户的不同客户、不同租户的同名客户都不得互相检索。缺少任一身份字段时返回空结果并记录诊断事件。

审核链路：退款工具生成持久化的 `review_request`（工单、租户、客户、订单、金额、原因、状态和时间）并设为待审核；事务提交后通过 outbox 发布审核事件。管理端待审核列表和详情展示证据，管理员点“批准放行”或“驳回”并填写原因；后端检查 RBAC、租户归属、订单归属和请求版本，原子地完成 `pending -> approved/rejected`，记录操作人、时间和理由。批准后只派发一次携带限定工单/订单/金额的授权任务；Agent 工具再次验证数据库审核记录，然后更新原型状态。用户侧得到等待和结果事件。

推送建议先做站内审核队列 + 管理端 SSE（或短轮询），保证本地演示可见；随后接企业微信/飞书或邮件通知负责人。外部通知只发送工单号、金额、跳转链接和最少必要信息，发送失败可重试，不影响审核记录。终端 `print` 仅用于开发诊断。

## 里程碑和验收标准

M0～M3 以下日期为 2026-10-05 制定时的原计划；隔离原型的实现和验收现状以文首更新及 2026-10-07 记录为准，不等于旧库迁移或正式上线。

### M0：身份与事件契约（建议 2026-10-05～10-06）

- 定义单租户迁移用的默认 `tenant_id`，确认未来租户来源和管理员所属租户。
- 在 `User`、`Order`、`Ticket` 添加租户字段及迁移；API 必须从可信身份取得 `tenant_id/customer_id`，移除 `payload.customer_id` 兜底。
- 创建统一请求上下文；独立 `ticket_id`、`request_id`、OTel trace ID，span/log 附加租户和经脱敏或内部化的客户标识。
- 验收：无法提供有效租户身份的请求被拒绝；跨租户订单/工单查询不可见；同一请求能用 trace ID 关联 API 与 worker，日志不输出原始敏感内容。

### M1：记忆作用域与存量迁移（建议 2026-10-07～10-09）

- 修改 `memory_gateway.py`、`extract_and_store_memory`、`search_user_memory`，在归档任务和 Qdrant 文档中传/存 `tenant_id + customer_id + ticket_id`，读取时双重过滤。
- 旧 `session_id` 文档先通过工单表核对归属再补齐元数据；无法确认归属的文档隔离，不在新查询中返回。迁移前保留备份与数量记录。
- 明确是否保留“仅本工单记忆”作为独立工具或检索选项，避免把未经证实的 Agent 回复写成永久客户事实。
- 验收：同一客户跨工单能检索授权记忆；同租户其他客户与其他租户完全检索不到；身份缺失时失败关闭；迁移前后数据量及抽样归属可核对。

### M2：审核后端与可靠通知（建议 2026-10-10～10-13）

- 增加 `review_requests`、`review_audit_events`、`notification_outbox` 表和迁移；将 `escalated` 与审核请求创建放入一致的事务。
- 增加管理员待审核列表/详情、批准和驳回 API；每个接口校验租户、角色、订单归属和版本。现有 `/ticket/approve` 可兼容，但应改由持久化审核记录驱动。
- 批准接口做原子状态转换和幂等派发；失败可重试且不会生成第二次放行。将管理端事件写入单独的审核事件流；通知 worker 消费 outbox。
- 验收：普通用户不能查看/审批；其他租户管理员不能审批；重复点击仅形成一次有效决策和一次派发；驳回不执行退款；通知失败可重试；审计记录完整。

### M3：人工审核界面与演示闭环（建议 2026-10-14～10-16）

- 做最小管理员页面：登录、待审核列表、详情证据、批准放行与驳回按钮、原因输入、操作结果；显示“仅更新原型数据库，未实际退款”。
- 管理端通过 SSE 或短轮询收到新审核请求；客户端展示等待审核及最终状态。外部推送通道在确定企业微信/飞书/邮件目标后接入。
- 演示流程：客户提交退款 -> 审核请求入队并推送 -> 管理员查看证据并批准/驳回 -> Agent 根据批准结果继续 -> 客户和审计页可看到结果。
- 验收：无需查看 VS Code 终端即可完成上述演示；按钮状态能防重复点击；失败、过期、已处理场景给出明确提示。

### M4：故障路径与稳定性评估（建议 2026-10-08～10-11，进行中）

- **先完成可控故障样例**：在隔离环境让 Agent 输出“已提交人工审核”，但不创建审核记录；再构造“已转交人工”但无转交记录的回复。核对 worker 返回 `error`、`/task/{task_id}` 返回 `failed`、任务事件为失败，且订单、审核和工单状态没有被误改。故障注入必须只作用于合成工单，报告保存输入、输出、任务 ID 与持久化状态。
- **再扩充端到端数据集**：从现有 10 条增至至少 20 条，覆盖退款措辞变体、混合售后/越权话术、工具异常、审批驳回与重放、未绑定订单、跨客户/跨商户访问；保留每条预期和 badcase 归因。每条重复运行至少 3 次，分开统计业务完成、权限边界、无依据承诺和执行后改写次数。
- **补可观测指标**：报告每条的工具调用序列、最终回复、数据库/审核状态、任务状态、耗时和模型用量；能取得用量时统计成本与延迟分布，缺少字段时明确标为未观测。原始模型行为与固定答复/拦截后的系统结果分别计数。
- **验收**：可控故障能稳定复现且用户界面不会显示“已完成”；样例中无跨租户数据泄露、无未审批退款、无无记录的成功承诺；报告含分母、重复次数、失败明细与修复前后对比。通过这些样例仍不能推断生产成功率。

## 实施顺序与决策点

当前顺序：M0～M3 隔离原型已完成 → M4 可控故障与重复评估 → 普通工单人工转交队列和管理端处理入口 → 旧库迁移/恢复演练与部署准备。外部通知渠道和真实支付对接在确定产品范围后另行规划。

已确定商家/企业是租户，同租户同客户的已验证偏好可跨工单复用。下一决策点是普通工单人工转交的负责人和处理入口；外部通知渠道尚未选定，M4 不依赖它。

自动提醒已按用户要求取消；后续由用户与助手人工核对进度。

### M2 后端接口审查与实施入口（2026-10-05）

- 当前 process_large_refund 只把工单标成 escalated 并在终端打印提示，没有持久化审核请求；/ticket/approve 核对管理员角色、二次凭据、工单与订单归属后立即派发 Agent。没有批准/驳回状态记录、审核人审计、待审核列表，也没有事务级防重复派发。退款工具目前只验证队列携带的结构化授权，尚未回查持久化批准记录。
- 下一步先建 review_requests、review_audit_events、notification_outbox 三张表。review_requests 对 ticket_id 加唯一约束，记录商户、客户、订单、金额、状态和版本；audit 记录每次决定的人、理由和时间；outbox 记录只需派发一次的审核事件。
- 退款工具应在同一数据库事务中创建 pending review 并把工单改为 escalated；管理员批准/驳回接口应对同租户 pending review 加行锁并原子更新，提交审计和 outbox。批准后的 worker 必须回查 approved review、订单及金额再更新原型退款状态。重复批准只得到已处理结果，不生成第二次派发；驳回不派发退款。
- 管理端先做同租户待审核列表与详情；新增事件通过站内队列及管理端 SSE/短轮询展示。外部企业微信、飞书或邮件通知在确定目标后接 outbox。现有 M2 三条合成验收用例可从跨商户批准、重复批准、驳回开始实现。
