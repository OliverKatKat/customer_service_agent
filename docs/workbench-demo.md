# 耳机店轻量演示

这里使用一个虚构耳机店，初始样本为28笔订单、14个案件、15次联系和8个账号。第二商家的4笔订单、2个案件只用于展示隔离，不需要真实业务数据。

## 一条命令准备并启动

先确保 Docker Desktop 已启动，在项目目录执行：

```powershell
Set-Location -LiteralPath 'D:\Agent构建与评估 - 进化'
.\.venv\Scripts\python.exe scripts/run_workbench_demo.py
```

打开 `http://127.0.0.1:8001/demo`。脚本创建独立的演示服务，应用迁移、写入样本并配置只读统计，不修改原来的 agent_db 和 app/.env。仅准备数据可加 `--prepare-only`；API 端口可通过 `--port` 调整。

演示账号统一使用初始化时的 `DEMO_PASSWORD`。默认口令为 `EchoDemo2026!`，只用于这套隔离的虚构数据。主管的二次审批凭据默认是 `demo-only-approval-20261028`，实际值同时显示在启动终端和忽略提交的 `infra/workbench-demo/.env` 中。

| 账号 | 用途 |
| --- | --- |
| demo_echo_alice | 演示客户，三个主要故事都可用这个账号 |
| demo_echo_staff | 查看案件、领取待办、备注、整理审核材料 |
| demo_echo_admin | 主管，查看工作台并在原审核页批准或驳回 |
| demo_echo_analyst | 只读台账统计 |
| demo_echo_bob 和 demo_echo_carol | 补充客户样本 |
| demo_nova_alice 和 demo_nova_admin | 第二商家的隔离样本 |

脚本继续使用 app/.env 中现有模型配置，不复制或打印模型密钥。正常对话和模型草稿会按需调用现有模型。演示使用本地 BM25 检索虚构政策，不需要先给样本生成向量。若未检测到模型密钥，会启动数据浏览模式：可查看样本和事实材料，但不派发聊天和审批任务，不把模板冒充模型输出。

按 Ctrl+C 结束由本次命令启动的 API、worker 和 beat。数据库样本保留，下次启动不会重置已经写下的备注、人工分类或订单处理结果。需要停止演示容器时执行：

```powershell
docker compose -p workbench-demo --env-file infra/workbench-demo/.env -f infra/workbench-demo/compose.yaml stop
```

## 三条故事怎么演

| 故事 | 样本 | 操作和核对点 |
| --- | --- | --- |
| 未发货申请退款 | DEMO-ECHO-001，CASE-DEMO-REFUND | 专员查看联系和材料；主管进入原审核页处理待审申请；回到详情核对批准与模拟执行状态 |
| 已发货不能直接退款 | DEMO-ECHO-002，CASE-DEMO-SHIPPED | 客户提问时应引用商家政策并说明物流需要人工核实；原型工具不得直接把订单改成 refunded |
| 同一申请继续联系 | DEMO-ECHO-003，CASE-DEMO-REPEAT | 从演示页进入客户对话，申请编号会明确显示；发送补充信息后，专员应看到同一案件下新增联系 |

客户页支持“继续此申请”和“新建申请”。切换订单会清空关联申请编号，避免把另一个订单的请求误合并。没有填写 case_id 时，仍按原协议新建申请。

待审核、已批准、已完成和已驳回的部分记录是初始化时预置的合成历史，便于随时展示界面；它们不是这次启动后模型实际跑出的结果。真正的交互结果以数据库状态和对应审计记录为准，模拟 refunded 也不代表真实支付到账。

## 审核材料做了什么

在案件详情点击“整理审核材料”。系统读取本商户订单、最近联系和审核事实，并从本商户政策中检索依据。订单和审核事实不交给模型改写；模型只生成供人工核对的摘要、注意事项和下一步建议。

模型返回不合法字段、虚构引用或无依据的退款完成承诺时，退回事实模板；超时或无模型配置时也明确显示事实资料。材料不会自动批准、改订单或关闭案件。响应包含使用的案件版本，生成期间发生更新时会提示重做。

接口为 `POST /api/v1/workbench/cases/{case_id}/material`，请求 `{ "use_model": true }`。只想读取事实和政策可传 false，不调用模型。接口仅限本商户 staff/admin。

## 三至五分钟讲解顺序

1. 用半分钟说明“售后人员接手时要反复找订单、翻政策、问之前谁处理过”。展示待办和案件详情。
2. 用一分钟展示未发货退款材料：客户诉求、订单事实、政策依据、人工备注。说明模型只辅助整理，决定由人工做。
3. 用一分钟演示主管审核和后续状态；讲清 pending、approved 与模拟执行完成的区别。
4. 用一分钟展示已发货申请的处理边界，以及重复联系如何显式归入同一案件。
5. 最后展示简单台账计数和验证结果。说明数据为合成样本，讲一个自己实际修复的问题，例如跨客户关联、并发版本或错误政策引用。

如果还未配置可用模型，先用预置历史和事实模板讲清流程；不要把该演示称为真实模型端到端评测。当前已附讲解脚本，尚未录制真实模型演示视频。

## 数据和验证

固定样本位于 `demo/workbench.json`，商家政策位于 `company_knowledge/tenants/demo_echo/handbook.txt`。商品名称只作为演示上下文写在原始联系与备注中，本版没有新增商品仓库或经营分析数据层。

新增检查包括样本重复初始化、保留人工修改、标识冲突拒绝、材料权限和政策隔离、虚构模型引用降级、模型草稿不改订单、浏览模式不派发任务，以及真实退款工具拒绝已发货订单。加上原有工作台检查，共32项。

验证命令仍是 `scripts/run_workbench_tests.py`。测试库为独立的55458端口；演示库为55459端口、Redis为56380、Qdrant为56335，均绑定127.0.0.1。测试使用模型替身验证接口和失败边界，不产生外部模型调用；模型实际质量和延迟需要另行运行观察。


## 统一登录与新版前端

`/demo` 为场景介绍页，`/login` 为统一登录页。客户 user 登录后进入 `/chat`，专员 staff 进入 `/workbench`，主管 admin 默认进入 `/review`，分析员 analyst 进入工作台统计。主管可通过侧栏进入案件和统计，并沿用当前登录。

页面导航和刷新使用当前标签页的会话存储保留 JWT。页面启动均向 `/api/v1/users/me` 核对数据库中的实际角色；后端继续逐请求校验身份、商家和权限。退出会清空本页数据，并通知其他同源窗口退出。场景参数仅允许本站指定工作页面，登录不会跳转外部地址。

首页的演示账号按钮只预填账号，仍需输入密码。客户可以点击示例问题填入输入框，确认发送才调用 Agent。专员可以整理材料、展开政策依据、添加备注和跟进待办；主管的审核决定仍需原有二次审批凭据。演示数据与启动方式沿用上文。


物流 MCP 已接入已发货场景，启动方式不变，数据和工具链见 [物流 MCP 说明](logistics-mcp.md)。
