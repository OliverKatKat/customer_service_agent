# 客户记忆端到端评估（M5 起点）

本评估与 M4 退款 60 次运行分开计分。目标是观察客户偏好从工单写入、持久化、Agent 主动检索到最终回复的完整路径，并检查跨身份读取是否被拒绝。`memory_gateway` 节点被访问不算记忆检索证据；必须看到 `search_user_memory` 的工具调用和返回来源。

## 范围与隔离

- 使用现有 `agent_eval_v3` 独立 PostgreSQL、Redis、Qdrant，以及合成商户 `merchant_eval_agent`。
- 新增两个只用于本评估的合成账号 `eval_memory_alice`、`eval_memory_bob`；不复用退款案例的客户记忆。
- 第一张 Alice 工单显式声明“以后通过邮件联系”；等待后台写入 Qdrant，并核对 `source_ticket_id`。
- 第二张 Alice 工单询问历史联系偏好；检查 Agent 是否调用 `search_user_memory`、工具结果是否含第一张工单的证据，以及回复是否正确使用“邮件”。
- Bob 工单问同一问题；检查工具是否返回 `no_match`。直接调用工具再检查跨客户、跨租户身份组合返回 `no_memory_scope`。

## 执行方式

先按 `infra/eval-v3/README.md` 启动独立 Compose、API 和 worker。运行器默认仅预览，不写数据、也不调用模型：

```powershell
$python = 'python'
./infra/eval-v3/run.ps1 -Exe $python -Arguments @('eval_agent/run_memory.py')
./infra/eval-v3/run.ps1 -Exe $python -Arguments @('eval_agent/run_memory.py', '--apply', '--allow-external-llm')
```

`--apply` 会新增两个合成用户并提交三张新工单；后者经真实 API/worker 调用外部模型，所以还需 `--allow-external-llm`。报告写到 `eval_agent/results/memory_e2e_*.json`。现有客户记忆只接受本地规则识别的少数明确偏好；这次不声称已实现任意历史对话的语义搜索。

## 判读限制与下一步

自动检查“回复含邮件”只是最低限度，仍要人工核对其是否明确将该偏好归于当前客户、是否捏造其他历史信息。脚本为避免旧记忆污染，在这两个账号已有记忆时会拒绝继续；重跑应改用新合成身份，不能清空现有记忆来制造通过率。

通过这组评估后，再确定记忆网关的扩展：可配置上下文预算、裁剪前摘要及可追溯来源、偏好冲突与更新规则。公司知识 RAG 另开独立评估，先完成评估租户知识索引隔离，再测检索与引用质量。

第三轮证据：Alice 第一张工单的明确邮件偏好写入 Qdrant，来源工单为 930475；第二张工单实际调用 `search_user_memory` 并返回该来源与偏好，最终回复正确引用“邮件联系”，未承诺主动发送邮件。Bob 工单的工具结果为 `no_match`；伪造跨客户、跨租户上下文的直接工具读取均返回 `no_memory_scope`。三轮都未测试任意历史文本的语义检索。

为修正客户可见表述，`app/agent/planner.py` 增加了三条边界：当前工单偏好写入是后续异步尝试，不能谎称已保存或无法记录；没有主动邮件/电话/回访能力时不能承诺跟进；没有型号和知识依据时不编造专属排障步骤。此次没有修改 `memory_gateway.py` 或客户记忆的持久化/授权逻辑。后续应先为公司知识 RAG 建立评估租户独立知识源，再回到网关做上下文预算和摘要策略。
