# M4 退款状态与回复一致性优化（2026-10-18）

## 目标

处理已发现的表达风险：数据库中审核仍为 `pending`、订单仍为 `paid` 时，模型可能先说“退款申请我已经处理好了”或“已为您处理完毕”，后文才补充尚未退款。该措辞容易让客户误以为退款已经完成。

## 修改

- 在 `app/agent/reply_guard.py` 增加退款完成/模糊完成措辞识别、待审核状态披露识别，以及短语级归一化。只替换冲突短语，尽量保留混合意图回复中的其他内容。
- 在 `app/workers/tasks.py` 增加租户、客户、工单、订单作用域下的持久状态复核。只有 PostgreSQL 确认审核仍为 `pending` 且订单仍是 `paid` 或 `out_of_stock` 时，才改写含糊的完成措辞；数据库状态保持原样。
- 在 `eval_agent/run.py` 与 `aggregate.py` 增加独立的 `reply_quality_metrics`，检查是否说明审核进行中、是否出现退款完成声明、订单是否仍处于预期状态。该诊断不改变原有 `passed` 与 59/60 评分口径。
- 新增 `eval_agent/test_reply_guard.py` 覆盖两种歧义措辞、明确待审核措辞、历史已退款状态及保留混合回复其他内容。

原源码已复制到 `docs/source-backups/20261018-reply-consistency/`。M4 v1.5.0 数据和旧报告未覆盖。

## 新发现的问题与取舍

- 21 条针对性待审回复中有 19 条提到实际到账时间“以支付渠道为准”。当前系统未接入真实支付网关，这类措辞容易暗示存在可追踪的到账流程。此问题未修复，后续应针对未接支付网关的场景制定回复约束和独立评估项。
- 历史 2/21 歧义措辞降至离线回放 0/21，属于同一批已保存文本的规则效果；新端到端 21/21 安全回复和完整回归 59/60 属于新样本结果。两者不能直接当作线上同比提升或生产成功率。
- `eval_agent/aggregate.py` 新增显式 `--report` 选择，避免把旧报告混进本轮汇总；汇总保留每份原始报告和机器原判。

## 下一步

1. 将“尚未接入支付网关时不得暗示到账时间可确认”加入回复约束，并以独立坏例验证；先保存当前 19/21 作为基线。
2. 改进 `E2E-ALREADY-REFUNDED` 的评分规则，区分历史退款事实与 Agent 声称本轮新退款；版本化保存规则并复跑同一案例。
3. 在简历或面试展示中分别标注离线回放、固定故障注入、真实 Agent 触发和完整回归，避免混用分母或声称未经验证的生产提升。
